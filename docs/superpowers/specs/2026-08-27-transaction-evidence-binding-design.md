# 交易证据强关联与回复发送门禁设计

## 背景

2026-08-27 的 DevaPay 生产回复暴露了一类高风险证据关联错误。运营截图展示“XDPay 印度收款”、金额 100，客服回答却把一笔同金额的 AOHPay 代付订单 `DF...` 当成同一笔交易，并据此确认“通道配置已经生效”和“页面没有识别成功结果”。随后运营明确表示无法找到该订单。

最新发布的 DevaPay 双仓代码确认，代收成功响应包含 `codeUrl`、`deepLink`、`utr`、`upi`、`orderNo`、`merchantNo`，代付成功响应才包含 `orderNo`、`orderAmount`。原回答同时存在交易关联、业务类型和通道主体三处冲突。

当前系统已经区分消息、截图、代码、请求、响应、回调和运行证据，也保存 `evidencePacket` 与回复生成审计，但仍有两个缺口：

1. 证据包没有表达“这些运行记录是否已被证明属于用户正在问的同一笔交易”。
2. 普通直接回答不进入独立回复审核；现有多阶段审核失败时还可能退回未经独立审核的调查模型基线答案。

## 目标

- 金额、时间、收款人、通道名称等搜索线索只能用于寻找候选，不能单独确认同一笔交易。
- 只有我方系统订单号、商户订单号、上游订单号、银行交易参考号或可复核请求 ID 至少一项在两个可信来源中完全一致，才允许确认交易关联。
- 代收、代付、服务、商户或通道发生冲突时，候选订单不得成为对外事实或因果依据。
- 所有引用具体交易运行事实或从运行事实派生因果结论的回复，在发送前必须经过结构门禁和独立审核。
- 证据不足时由回答模型自然生成最少追问或边界说明，不在代码中拼接固定业务文案。
- 保持现有线程归档、补充消息作废、人工接管、进度提示、发送所有权、技术告警和失败恢复语义不变。
- 不增加新的 SQLite 表，不把生产凭据、完整报文或附件实体写入测试夹具。

## 非目标

- 不自动合并或重新打开超过 30 分钟已归档的问题线程。
- 不因为历史线程内容相似就把它当成本轮运行证据。
- 不用关键词、正则、相似度、分数或固定错误码判断代收代付、责任、是否升级或业务根因。
- 不修改 DevaPay、其他四方支付服务、生产数据库或生产业务配置。
- 不为本次低频缺陷建设全量生产对话评测平台。

## 设计原则

业务语义仍由回答模型结合当前服务代码和只读证据判断。父进程只校验模型已经声明的结构关系是否自洽，不用确定性代码代替业务判断。

父进程可以安全执行以下中立约束：

- 被声明为“已确认关联”的交易必须引用允许的稳定标识。
- 匹配标识必须真实存在于至少两个被引用事实中，类型和值完全一致，来源不同且都不是推断。
- 金额、时间、姓名、账户、商户或通道本身不能充当交易唯一标识。
- 被声明为存在业务类型、服务、商户或通道冲突的关联不能同时标记为已确认。
- 未确认或冲突关联下的具体订单事实不能进入最终客服事实声明。

## 数据契约

### 证据事实

`EvidencePacket` 升级为版本 `2`。每个事实除现有来源、置信度和出站属性外，增加：

```ts
type EvidenceSubjectKind = "general" | "transaction" | "configuration" | "merchant" | "channel"
type EvidenceBusinessType = "collection" | "payment" | "unknown" | "not_applicable"
type StableIdentifierKind =
  | "system_order_no"
  | "merchant_order_no"
  | "upstream_order_no"
  | "bank_reference"
  | "request_id"
type LookupHintKind = "amount" | "time" | "recipient" | "account" | "merchant" | "channel"

type EvidenceIdentifier = {
  kind: StableIdentifierKind
  value: string
}

type EvidenceFact = {
  // 原有字段省略
  subjectKind: EvidenceSubjectKind
  businessType: EvidenceBusinessType
  identifiers: EvidenceIdentifier[]
  associationId: string | null
  dependsOnFactIds: string[]
}
```

事实来自 `inference` 或 `certainty=inferred` 时，`dependsOnFactIds` 至少包含一项。父进程只允许依赖当前证据包中存在的事实，禁止循环依赖。

### 交易关联

证据包增加 `associations`：

```ts
type EvidenceAssociation = {
  id: `A${number}`
  subjectKind: "transaction"
  status: "confirmed" | "unconfirmed" | "conflicting"
  factIds: string[]
  matchedIdentifiers: Array<{
    kind: StableIdentifierKind
    value: string
    factIds: [string, string]
  }>
  lookupHints: Array<{
    kind: LookupHintKind
    value: string
    factIds: string[]
  }>
  conflicts: Array<{
    field: "business_type" | "service" | "merchant" | "channel" | "identifier"
    leftFactId: string
    rightFactId: string
    summary: string
  }>
}
```

`matchedIdentifiers` 只能使用以上五类稳定标识。银行 UTR、RRN 或等价银行流水标识统一登记为 `bank_reference`，但必须由当前代码和证据确认字段含义，不能仅因任意文本看起来像流水号就归类。所有标识仅做安全裁剪首尾空白后逐字匹配，不改变大小写、前导零、连字符或其他字符。`lookupHints` 可以保留金额、时间等候选检索信息，但永远不能把 `status` 提升为 `confirmed`。

### 回答事实引用

正式回答模型输出的每个 `answerClaim` 增加必填 `factId`。为兼容现有测试夹具，Zod 输入层可以暂时接受缺少 `factId` 的旧夹具，但生产 JSON Schema 必须要求该字段。

已有审计记录继续作为不透明 JSON 保留。新运行写入 `evidencePacket.version=2`，因此不需要 SQLite 迁移。

## 父进程结构门禁

新增独立模块 `src/support/evidence-binding-gate.ts`，返回信任化证据包、可修订问题和不可恢复结构错误，只负责以下纯结构判断：

1. 验证事实 ID、关联 ID、依赖 ID 和引用 ID 都存在且不重复。
2. 验证推断依赖无循环。
3. 验证 `confirmed` 交易关联至少存在一个稳定标识匹配。
4. 验证匹配标识在两个非推断事实中均以相同类型和值出现，并且证据来源不同。
5. 验证 `confirmed` 关联没有未解决的业务类型、服务、商户、通道或标识冲突。
6. 同一稳定标识若指向多个不同系统订单且证据包未声明并解除冲突，不允许确认关联。
7. 将没有稳定匹配却声明为 `confirmed` 的关联安全降级为 `unconfirmed`，记录可修订问题，并把相关具体交易事实强制改为 `outboundSafe=false`。
8. 将已声明业务类型、服务、商户、通道或标识冲突的关联规范为 `conflicting`，并把相关具体交易事实强制改为 `outboundSafe=false`。
9. 如果推断事实依赖不可出站的交易事实，也将该推断强制改为不可出站。
10. 最终回答中的每个事实声明必须引用现存且可出站的 `factId`。

引用不存在、事实或关联 ID 重复、推断依赖循环等情况属于不可恢复结构错误，不能依赖不完整证据包重写业务答案；沿现有模型结构失败机制自动重试一次。稳定标识不足或业务对象冲突属于可安全降级问题，保留截图、当前服务代码和配置等仍可信事实用于生成最少追问或边界说明。

代码不检查“XDPay”“AOHPay”“代收”“代付”等具体词，也不根据订单前缀猜业务类型。业务类型和冲突由模型按当前代码、消息与运行证据声明，父进程只验证声明之间是否自洽。

## 回复流水线

### 适用范围

以下任一结构条件成立时进入严格证据审核：

- 证据包包含 `transaction` 关联。
- 最终声明引用 `request`、`response`、`callback` 或 `runtime` 事实。
- 最终声明引用依赖上述事实的推断。
- 本轮责任判断不是 `unknown` 或 `not_applicable`。

这些条件来自结构化来源字段，不解析客服正文。

### 执行顺序

1. 调查模型生成基线决定、版本 2 证据包和带 `factId` 的声明。
2. 父进程信任化调查轨迹、脱敏证据包并执行结构门禁。
3. 结构门禁产生可安全降级问题时，基线答案不得成为回退答案；门禁问题和信任化后的证据包作为修订反馈交给独立回复模型。结构门禁遇到不可恢复结构错误时沿现有结构校验失败机制重试调查模型，不使用损坏证据包继续生成。
4. 结构门禁通过且不需要严格审核时，沿用现有直接回答流程。
5. 需要严格审核时，独立审核模型同时检查基线正文、事实引用、关联状态和未知边界。
6. 第一次审核通过，使用基线答案。
7. 第一次要求修订，由独立回复模型只使用可出站事实重新生成一次，再执行结构门禁和第二次审核。
8. 第二次通过，使用修订答案。
9. 第二次仍不通过，或严格审核/修订模型失败，抛出 `SupportModelOutputRejectedError`，不得退回基线答案。

现有 `prefer_baseline` 只能用于已经通过结构门禁和本轮独立审核的基线；不能作为审核失败后的安全回退。流水线审计版本升级为 `evidence-binding-review-v2`，继续写入现有 `reply_generation_audits`。

### 缺少稳定标识

缺少稳定标识不等于处理失败。调查模型应把关联标记为 `unconfirmed`，把候选订单事实保留为内部不可出站信息，并在 `unknowns` 中说明缺少的唯一定位信息。回复模型根据当前服务事实选择：

- 追问一个能够核验我方请求、响应、回调或状态的最少业务标识；或
- 当前服务确认不存在相关业务对象且答案只在外部系统时，直接说明边界并收口。

父进程不拼接固定追问文案。

## 当前 DevaPay 场景的预期行为

输入事实：

- 截图展示 XDPay 印度收款、金额 100。
- 候选运行记录为 AOHPay 的 100 元代付订单。
- 两侧没有共同系统订单号、商户订单号、上游订单号或请求 ID。

预期关联：

- `status=conflicting`。
- 金额和时间只登记为 `lookupHints`。
- 业务类型和通道登记为冲突。
- 候选 `DF...` 订单及其成功、回调事实全部为内部不可出站。
- “通道已生效”“调用页面没有识别成功结果”等依赖候选订单的推断不可出站。

预期客服意图为最少追问或服务边界说明。允许的自然回复示例：

> 这张图目前还对应不到 DevaPay 的具体订单。截图显示的是 XDPay 印度收款、金额 100，但金额相同不能证明是同一笔，所以现在不能判断通道已经生效，也不能确定是哪边的问题。把这次充值的商户订单号发我，我按这一笔核对 DevaPay 有没有收到请求、实际走的通道和当时返回的结果。

示例只表达语义，不作为固定模板或测试中的逐字断言。

## 并发、作废和人工接管

严格审核和修订仍属于同一个回复生成任务：

- 输入修订号变化时，旧基线、审核和修订结果全部标记为 `superseded`，不得发送。
- 审核期间人工接管时，沿现有取消信号停止生成并放弃发送所有权。
- Telegram 发送请求开始前必须再次核对线程修订号、终态和输出所有权。
- 进度消息的一次性语义不变；如果已经发送进度后发生两次审核拒绝，沿现有处理失败转技术流程收口。
- 未发送进度且审核拒绝时保留明确失败状态和审计，不伪装成已回复或已关闭。
- 产品需求、专人操作和人工接管仍按现有升级边界处理，证据关联门禁不得改变其业务语义。

## 提示词与固定规则

更新 `AGENTS.md`、`src/support/system-directives.ts` 和 `src/support/agent.ts`，统一加入以下语义：

- 金额、时间、姓名、账户、商户或通道只能用于寻找候选，不能单独证明同一交易。
- 引用具体订单状态、通道、请求、响应或回调前，必须确认至少一个稳定交易标识；银行参考号只有在当前代码和证据确认字段含义时才属于稳定标识。
- 不能用另一业务类型、另一服务、另一商户或另一通道的候选订单解释当前截图或报错。
- 找到同金额订单不等于请求已经进入我方，也不能据此确认配置生效或外部页面处理错误。
- 证据不足时保留未知边界，只追问当前核验我方事实所需的一项最少标识。

同一语义只保留一个系统固定规则权威来源，回答模型使用代码内编译后的同一份规则；不得通过关键词表、正则或错误码特判本次案例。

### 聚焦历史回放

不做全服务大规模抽样。使用生产 SQLite 的只读副本，在无 Telegram 输出适配器的隔离环境中聚焦回放：

- 本次 DevaPay 截图线程。
- 前一条包含 `danid`、`ptype` 和空白返回的已归档线程。
- 后续“找不到订单”和人工接管线程。
- 少量现有带附件、缺少订单号或同金额候选的对话。

报告只保存脱敏 case ID、结构审查结果、是否引用不安全事实和最终决策，不保存原始附件、密钥、签名、连接信息或完整聊天正文。

## 验收标准

- 当前 DevaPay 事故夹具不能引用 AOHPay 代付订单或其状态。
- 金额和时间不能单独形成 `confirmed` 交易关联。
- 正确稳定标识匹配仍能正常回答真实订单状态，不造成一律追问。
