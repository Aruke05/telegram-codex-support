# AI 对话终止与双仓错峰同步设计

## 目标

本次同时优化后台 `AI 对话` 的操作闭环和 AI 客服使用代码快照的方式：

1. 等待中或生成中的后台对话可以真正终止，并保存明确的 `cancelled` 终态。
2. 服务选择器进入对话工作台顶部；没有消息时输入区靠近服务选择器，不再横跨整个页面高度。
3. 已选择服务但未选择会话时，第一次发送自动原子创建会话和首个问题，不再要求先点击 `新对话`。
4. Telegram 客服回答和后台 AI 对话不再触发 Git 拉取，只读取当前服务最近一次成功发布且仍匹配当前配置的完整双仓快照。
5. 代码定时同步改为每个服务每 30 分钟一次，并在全局单并发队列中分批错峰执行，避免多个服务或其他触发来源同时访问 GitLab。

Peakpay 继续永久排除。业务代码、生产服务器和生产数据库继续只读。

## 成熟方案调研

### AI 生成终止

Vercel AI SDK 的 `useChat` 在 `submitted` 和 `streaming` 状态显示 Stop，调用后通过 AbortSignal 中断请求，并在完成回调中区分 `isAbort`、断线和普通错误。OpenAI Realtime API 的 `response.cancel` 也会把运行结果明确标记为 `cancelled`，而不是普通失败。Node.js 的 AbortController 是稳定 API，`abort()` 会向整个调用链发送一次取消信号。

可复用结论：终止必须同时具备用户可见操作、后端持久化终态和真实执行链取消，不能只在页面隐藏进度，也不能把人工终止混成系统失败。

参考：

- https://ai-sdk.dev/docs/ai-sdk-ui/chatbot
- https://platform.openai.com/docs/api-reference/realtime-client-events#realtime-client-events-response-cancel
- https://nodejs.org/api/globals.html#class-abortcontroller

### 会话首发体验

Vercel AI SDK 的 `useAssistant` 在没有 threadId 时提交消息会创建新线程；OpenAI 的 conversation state 指南也把会话状态视为多轮消息的承载方式，而不是要求用户先手工创建一个空壳会话。

可复用结论：`新对话` 是主动切断旧上下文的操作，不应成为第一次提问的前置步骤。首次提交应由服务端在同一事务中创建会话和首轮，防止只创建空会话或重复点击造成孤儿数据。

参考：

- https://ai-sdk.dev/docs/reference/ai-sdk-ui/use-assistant
- https://developers.openai.com/api/docs/guides/conversation-state

### 错峰与限流

GitLab 文档把速率限制作为保护服务耐久性、避免脚本或错误造成过量请求的基本手段。GitHub Actions 官方文档明确提示整点属于高负载时段，并建议把调度分散到小时内的不同时间。BullMQ 的并发控制同样区分任务速率和同时执行数量，说明只调整时间间隔不足以阻止并发峰值。

可复用结论：本项目需要同时限制“多久同步一次”和“同一时刻拉多少个”。只把一小时改成半小时但保留三服务并发，仍可能形成 GitLab 峰值。

参考：

- https://docs.gitlab.com/security/rate_limits/
- https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule
- https://docs.bullmq.io/bullmq-pro/groups/concurrency

## 方案比较

### 方案 A：前端顺序创建与失败状态复用

前端没有会话时先调用创建会话接口，再调用创建轮次接口；终止把轮次写成 `failed`。

优点是改动少。缺点是两个请求之间失败会留下空会话，重复点击可能创建多个会话，人工终止和系统失败混在一起，后续统计、重试和页面文案都不准确。

### 方案 B：原子首发、明确取消、快照读取与全局错峰队列

服务端提供一次提交服务和问题的原子首发接口；轮次增加 `cancelled` 状态；回答只读已发布快照；所有远端同步进入全局单并发队列，定时器每分钟领取一个到期服务，每个服务成功或失败后 30 分钟再到期。

这是采用方案。它直接解决三个页面问题，并同时消除回答、自动学习、手动同步和定时同步偶发并发访问 GitLab 的风险。

### 方案 C：引入外部任务队列

使用 Redis/BullMQ 保存同步和回答任务，提供分布式并发与速率限制。

这个方案适合多实例，但当前应用是单机单进程并使用嵌入式 SQLite。引入 Redis 任务队列会扩大部署和恢复复杂度，不符合当前边界。

## AI 对话页面

### 布局

页面标题保留在工作台上方。服务选择器从标题右侧移入对话工作台工具栏，与当前会话、新对话按钮处于同一个视觉区域。

当没有会话或当前会话还没有消息时，页面进入 `starting` 状态：

- 引导内容缩短并靠近工作台顶部；
- 输入框紧接引导内容，不固定在页面最底部；
- 选择服务后立即启用输入框；
- 窄屏使用两行紧凑工具栏，服务选择器占完整一行，会话记录和新对话按钮保持可触达。

一旦存在消息，恢复当前滚动消息区和底部输入框布局。浅色、深色、桌面和窄屏继续使用现有设计令牌。

### 首次发送

新增 `POST /api/admin-chat/turns`，请求为：

```json
{"serviceId":"<uuid>","question":"问题"}
```

服务端在一个 SQLite 事务中校验服务、创建会话、创建首轮、用首轮问题更新会话标题，并返回：

```json
{"session":{},"turn":{}}
```

已有会话继续使用 `POST /api/admin-chat/sessions/:id/turns`。`新对话` 按钮继续保留，用于用户明确希望切断当前上下文时创建空会话，但不再是第一次发送的必经步骤。

### 终止

`admin_chat_turns.status` 增加 `cancelled`，SQLite schema version 从 12 升到 13。迁移重建轮次表并保留全部字段、索引和外键关系。

新增 `POST /api/admin-chat/turns/:id/cancel`：

1. `pending` 轮次直接条件更新为 `cancelled`，不会再被工作器领取。
2. `generating` 轮次先条件更新为 `cancelled`，再调用工作器保存的 AbortController。
3. 已经是 `cancelled` 时幂等返回当前轮次。
4. 完成或失败恰好与终止并发时返回实际终态，不覆盖既有结果。

页面只在 `pending` 或 `generating` 时显示 `终止`。终止后显示独立的 `已终止` 卡片，可按现有方式重新排查。终止不是系统错误，不显示红色故障文案。

## 代码快照读取

`ProjectCodeSyncService` 增加只读 `readCurrentSnapshot(serviceId)`：

- 校验项目、服务、分支以及 `java-project`、`sfzf-web` 当前绑定；
- 找到当前配置指纹和仓库组合对应的最近一份完整发布快照；
- 复核目录边界、双仓 item、提交哈希、无 `.git` 和无符号链接；
- 读取产生该快照的有效同步批次 ID；
- 不访问网络、不创建同步批次、不修改调度时间。

Telegram 回答、后台 AI 对话和自动学习都调用该只读方法。快照即使来自 30 分钟内更早的成功同步也正常回答，不向运营声明已在本轮拉取最新代码，不因为定时同步最近失败而阻止回答或请求技术支援。

排查轨迹改为 `读取当前双仓快照`，展示分支、双提交、快照发布时间和快照 ID。只有没有任何匹配的完整快照或项目代码配置刚发生变化时，本轮才按现有运行失败边界诚实结束。

## 定时同步与全局背压

现有持久化到期表继续使用，列名 `next_hourly_sync_at` 作为兼容性内部字段保留，语义改为下一次定时同步时间。

调度行为：

- 每 60 秒扫描一次到期任务；
- 每次最多领取 1 个至少绑定一个启用客服群的服务；
- 领取时把该服务下一次到期时间推进 30 分钟；
- 同一服务的后端和前端仓库顺序 fetch，不再 `Promise.all`；
- `ProjectCodeSyncService` 增加全局单并发远端队列，定时、手动及仍可能存在的其他远端触发都必须排队；
- 同一服务重复请求继续复用既有 in-flight Promise；
- 一个服务失败不阻塞下一分钟的其他服务；相同错误继续只告警一次，恢复后发送一次恢复通知。

这种设计下，即使所有服务同时到期，也会按每分钟一个服务滚动处理，不会形成多个服务和四个仓库同时 fetch 的峰值。

## 文案和固定规则

后台文案统一改为：

- `代码每 30 分钟分批同步`
- `回答使用最近一次成功发布的双仓快照`
- `手动同步` 保留

固定规则删除“每次回答前先同步”和“同步失败不能回答”的旧约束，改成回答只读当前快照。当前代码快照仍高于旧记忆，但“当前”表示当前配置所指向的最近一次成功发布快照，不表示本轮刚执行过 Git fetch。

## 错误处理与恢复

- 服务重启时，遗留 `generating` 仍恢复为 `pending`；已经 `cancelled` 的轮次不恢复。
- 终止接口在数据库状态更新成功后即返回；AbortController 用于停止正在运行的 Codex、SSH 和数据库只读流程。
- 工作器发现 AbortSignal 已触发时不再调用普通失败处理，避免把 `cancelled` 覆盖成 `failed`。
- 定时同步失败保留上一份完整快照；回答继续使用旧快照。
- 手动同步仍返回 `fresh` 或 `fallback` 结果，方便管理员确认 Git 状态。

## 验证

项目约束禁止提交测试文件或测试代码。本次使用一次性临时脚本完成先失败后通过，脚本不进入 Git。

服务器验证至少覆盖：

1. schema 12 数据库迁移到 13 后已有会话和轮次完整保留。
2. 首次发送一次请求创建且只创建一个会话和一个 pending 轮次。
3. pending 终止后不能被领取；generating 终止会触发 AbortController；重复终止幂等。
4. 终止、完成并发时不会覆盖已经完成的结果。
5. 没有选中会话但选中服务时输入框可用，发送后自动打开新会话。
6. 空会话时服务选择、引导和输入区距离紧凑；有消息后恢复滚动布局。
7. 回答和自动学习读取快照期间没有新增 `answer` 或 `learning` Git 同步批次。
8. 调度器一次只领取一个服务，下一次到期推进 30 分钟；全局远端操作最大并发为 1；双仓顺序处理。
9. `pnpm typecheck`、现有 `pnpm test` 和 `pnpm build` 全部通过。
10. 部署后服务 active、健康检查正常、页面在浅色和深色以及桌面和窄屏无横向溢出。
