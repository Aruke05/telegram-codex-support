# 基于项目配置的代码定时同步设计

状态：已确认

日期：2026-08-11

## 目标

代码定时同步的资格只由项目管理中的项目和服务配置决定 不再依赖 Telegram 客服群是否启用或是否绑定该服务

一个服务满足以下条件时进入每 30 分钟错峰同步

- 所属项目已启用
- 服务已启用
- 服务配置了可用的 `java-project` 后端仓库和 `sfzf-web` 前端仓库 并使用同一个服务分支
- 服务不是 Peakpay

群配置只负责消息接入和回答服务归属 不再影响代码快照维护

## 现状与根因

调度器当前在读取到期服务时额外要求存在至少一个已启用的客服群 结果是项目管理中已经启用并完成双仓配置的服务 只要群未启用就永远不会被领取

生产数据中只有一个服务满足该群条件 因此它持续成功同步 其他服务的调度时间虽然已经逾期却始终被 SQL 过滤 这不是 Git 拉取偶发失败 而是调度资格与群配置错误耦合

## 方案选择

采用项目和服务配置直接驱动调度

- 删除调度查询对 `telegram_groups` 的依赖
- 保留项目启用 服务启用 Peakpay 排除 到期时间排序和一次只领取一个服务
- 双仓是否完整及仓库是否可用继续由已有同步服务做权威校验 配置异常时记录同步失败并按现有技术告警流程处理
- 不新增第二个自动同步开关 避免项目启用 服务启用和同步启用形成三套容易冲突的状态
- 不按仓库全局同步 因为一个服务必须由共同分支上的前后端双仓组成原子快照

这种做法与成熟的声明式源码同步一致 源码资源按自身配置和周期进行 reconcile 不以是否存在下游消费者作为拉取前提 同时继续保留当前全局串行和错峰机制 避免集中访问 GitLab

参考

- Flux GitRepository interval https://fluxcd.io/flux/components/source/gitrepositories/
- Flux source reconciliation https://fluxcd.io/flux/concepts/
- Kubernetes CronJob concurrency policy https://kubernetes.io/docs/concepts/workloads/controllers/cron-jobs/

## 数据流

1. 调度器每分钟扫描一次 `service_code_sync_schedule`
2. 从已到期记录中筛选已启用项目和已启用服务并永久排除 Peakpay
3. 按到期时间和服务 ID 排序 每轮只领取一个服务
4. 领取时先把下一次到期时间推进 30 分钟 防止重复领取
5. 进入现有全局串行同步队列 按顺序拉取该服务 `java-project` 和 `sfzf-web`
6. 双仓成功后发布或复用完整快照 失败时保留旧快照并按现有规则记录和告警

应用部署后 原先因群条件被跳过且已经逾期的服务会按每分钟一个自动补同步 不集中并发拉取

## 兼容性与错误处理

- 不修改 SQLite 表结构 已有逾期计划可直接生效
- 保留内部字段 `next_hourly_sync_at` 的兼容名称 实际周期仍为 30 分钟
- 停用项目或服务后不再领取新的定时任务
- 停用或删除群不再中断项目代码快照维护
- 双仓配置错误 仓库鉴权错误 分支不存在和网络错误继续由同步层分类 不在调度层静默忽略

## 验证

- 临时回归测试创建已启用项目和服务但不创建群 验证到期任务仍被领取
- 临时回归测试验证停用项目 停用服务和 Peakpay 仍被排除
- 在部署服务器执行类型检查 全量测试和构建
- 重启后读取生产同步记录 验证原先未绑启用群的逾期服务开始按每分钟一个补同步
- 验证服务健康接口和 systemd 状态正常

## 不在本次范围

- 不改变回答模型和群消息路由
- 不增加项目或服务页面字段
- 不修改手动同步行为
- 不把测试文件或测试代码提交到 Git
