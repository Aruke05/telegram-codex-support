# 专人操作请求客服承接与技术群真实转发设计

## 目标

创建账号、用户解冻及其他明确需要专人执行的操作不能再以 `ignore` 静默关闭。客服应先判断执行所需信息是否齐全：缺少关键标识时只追问当前最少需要的一项；信息齐全后生成自然、安抚且明确收到的运营回复，并通过现有 Telegram 转发能力把同一问题线程的全部原始消息真实转发到技术告警群。

本次统一处理所有明确由专人执行的操作，不只处理“创建运营账号”。客服不能声称自己已经完成实际操作，也不能只说“已转交”却没有发起真实技术群转发。

## 当前问题与根因

当前运行提示把“用户解冻、创建账号等明确由专人执行的操作”固定为 `decision=ignore`。模型在首轮可能先追问账号名称，但收到补充后仍受该固定规则约束，输出 `ignore`。结构化结果解析随后清空 `answer`，回答工作者把本轮标为 `ignored` 并关闭线程，因此运营看不到确认回复，技术群也没有收到请求。

远端最新代码已经具备以下可复用能力：

- 同一问题的补充消息会重新打开原线程，并保留完整原始消息。
- 普通持久升级会先 claim 技术告警 delivery，再把完整原始 Telegram 消息转发到技术群。
- 技术群投递状态使用持久 delivery row 和 Telegram output ownership 记录，可区分 `sent`、`not_configured`、`failed` 与 `uncertain`。
- 技术升级完成发送尝试后，再向运营群发送模型生成的最终回复。

因此根因在决策语义和升级证据门禁，不需要新建通知系统，也不应恢复技术群拼装告警文本。

## 行业方案调研

Chatwoot 的 Agent Bot handoff 会把机器人处理中的会话切换为人工可处理的 `open` 状态，记录等待时间并触发 handoff 事件。控制器把 bot 请求打开会话识别为 handoff，而不是继续让机器人静默结束。这个模式适合本项目：把“专人操作”建模为明确的人工接管类型，并复用当前持久投递和原消息转发链路。

Chatwoot 同时把会话状态与实际分派分开保存，说明“对用户确认已接收”和“后台是否成功通知人工”是两个需要独立审计的结果。本项目继续把运营回复状态与技术群 delivery 状态分别落库，不从客服文案反推是否已投递。

参考：

- <https://github.com/chatwoot/chatwoot/blob/develop/app/models/conversation.rb>
- <https://github.com/chatwoot/chatwoot/blob/develop/app/controllers/api/v1/accounts/conversations_controller.rb>
- <https://github.com/chatwoot/chatwoot/issues/12>

不照搬 Chatwoot 的坐席分配、在线状态或新收件箱模型。本项目只有一个技术告警群，现有 Telegram 原消息转发和持久 ownership 已能满足当前规模。

## 方案比较与选择

### 采用：独立 `human_operation` 升级类型

结构化回答新增 `escalationType=human_operation`。它只表达“客服不能直接执行、需要团队专人操作”，与代码缺陷、生产配置修改、产品需求和跨服务接管保持语义隔离。

优点：

- 不会误用 `technical_change` 的代码与生产运行证据门禁。
- 可以确定性要求消息证据和完整执行信息，同时不要求无关的代码排查。
- 继续复用持久 `escalation` delivery、崩溃恢复和原消息转发。
- 后台记录可清楚区分专人操作与故障升级。

### 不采用：复用 `technical_change`

`technical_change` 只适用于已经通过代码和运行证据确认、必须由技术修改生产配置、通道映射、后台数据或服务状态的情况。创建账号和用户解冻是业务操作请求，强行复用会迫使模型伪造无关证据或被服务端降级。

### 不采用：关键词直接转发

在路由层看到“创建账号”“解冻”就立即转发无法区分真实请求、引用历史消息和普通说明，也不能判断账号名、用户标识等必要信息是否齐全。决策继续由回答模型结合完整线程完成，服务端只验证明确的专人操作标记和消息证据。

## 决策规则

明确由专人执行的请求按以下顺序处理：

1. 从完整问题线程和最新消息确认运营当前要求执行的操作。
2. 判断消息是否已经包含执行该操作所需的最少业务标识。
3. 信息不足时使用 `decision=reply`、`escalationType=none` 和 `responseStrategy=minimal_clarification`，只追问一项最关键的信息，不转发技术群。
4. 信息齐全时使用 `decision=escalate`、`escalationType=human_operation`，由模型现场生成自然客服回复。
5. `humanOperation.action` 必须逐字摘取原线程中的操作请求片段，`humanOperation.identifiers` 必须逐项保存运营已经提供的必要业务标识；其他升级类型的 `humanOperation` 必须为 `null`。
6. `reason` 第一行必须独占一行写为 `[专人操作]`，后续说明操作类型、已取得的必要标识及为什么需要专人执行。
7. 服务端必须确认 action 和每个 identifier 都实际存在于完整问题线程；identifier 必须唯一、不能属于 action，并且必须在移除 action 后的消息内容中仍然出现。拒绝“用户、账号、运营、名称、编号、这个、怎么”等泛化或类别标识，不能把系统自动注入的通用 message 步骤当作信息齐全证明。
8. 调查轨迹必须至少包含一条 `source=message`、`status=confirmed` 的实际消息证据。专人操作保留当前已发布快照作为任务和服务归属上下文，但不要求读取代码内容或生产资源。

典型行为：

| 会话 | 判断 | 运营行为 | 技术群行为 |
| --- | --- | --- | --- |
| “创建一个新的运营账号” | 缺少账号名称 | 追问账号名称 | 不转发 |
| 后续补充“kakaxi” | 信息已齐全 | 确认收到并说明已转同事处理 | 转发原问题和“kakaxi” |
| “帮用户 12345 解冻” | 信息已齐全 | 确认收到并说明已转同事处理 | 转发完整原消息 |
| “用户怎么解冻” | 询问现有流程，不是执行请求 | 按当前知识回答 | 不转发 |
| “刚才说要创建账号” | 仅引用或描述，未要求执行 | 结合上下文正常判断 | 不因关键词自动转发 |

## 运营回复

`human_operation` 的 `answer` 由回答模型结合最新消息、固定风格 profile 和有效人工纠正生成，父进程不得用固定文案替换。回复必须满足：

- 以当班客服身份承接，明确已经收到当前操作信息。
- 自然安抚并说明已经通知技术同事接手。
- 已有账号名、用户 ID 等信息时直接承接，不让运营重复提供。
- 不承诺已经创建、已经解冻或给出未经证实的完成时间。
- 不写工单报告、技术分析或“系统无法执行”等推卸式说明。
- 真人口吻继续保持简短中文；AI 原始回复模式可按问题需要完整表达，但同样不得虚构完成结果。

针对确认场景，模型可以生成类似语义：

```text
收到 kakaxi 我已经发给技术同事处理了
```

这只是语义示例，不作为固定模板写入代码或提示词。

## 技术群转发与持久状态

`human_operation` 进入现有持久升级链路：

1. 将模型生成的最终运营回复和决策依据准备为持久升级记录。
2. claim `alert_kind=escalation` 的 delivery row。
3. 使用现有 `forwardMessages` 把问题线程中全部原始 Telegram 消息转发到技术告警群；补充消息必须一起转发。
4. Telegram output ownership 使用当前 reply、thread、service 和技术群归属，禁止通过解析 `decision_reason` 判断发送状态。
5. 保存真实 `sent`、`not_configured`、`failed` 或 `uncertain` 状态。
6. 完成技术群发送尝试后，向原群 reply 到起始问题发送模型原始 `answer`。

技术群继续只接收 Telegram 原消息转发，不新增拼装的“AI 客服告警”文本。群绑定服务通过持久线程和 reply 归属保留在后台，转发 ownership 仍携带 `serviceId`；不得在技术群额外发送可能与原消息割裂的系统说明。

发送结果为 `uncertain` 时不得盲目重发。崩溃恢复继续依据 delivery row 与 ownership：RPC 尚未开始才允许沿同一 reply 安全继续；已存在 `sent` 或 `unknown` ownership 时不得重复转发。运营回复失败仍使用现有独立 `support_delivery_failure` 处理，不因专人操作告警已存在而被抑制。

## 代码与规则改动范围

预计修改：

- `AGENTS.md`：把专人操作从“无需回复”改为“信息不足最少追问，信息齐全确认并真实转技术群”。
- `src/codex/schemas.ts`：为结构化回答和 JSON Schema 增加 `human_operation` 与 `humanOperation.action/identifiers`。
- `src/support/agent.ts`：更新专人操作判断、回复要求和 `reason` 格式。
- `src/support/investigation-service.ts`：验证 `[专人操作]` 与可信消息证据，不要求代码或生产证据。
- 现有相关测试夹具：仅在本地测试驱动阶段使用临时回归用例，按项目要求不提交临时测试文件或测试代码。

`src/support/answer-worker.ts`、`src/support/technical-alert-service.ts` 和数据库 schema 原则上不新增专用分支或新表；`human_operation` 通过已存在的普通持久升级路径真实转发原消息。若实施时发现远端最新代码对升级类型存在穷举分支，只做支持该类型所必需的最小调整。

## 错误与边界

- 技术告警群未配置、账号未配置或明确发送失败时，后台必须保留真实结果，不能写成 `sent`。
- 已发起真实转发但结果不确定时，不得为了满足客服文案重复转发。
- 新补充消息在生成期间到达时，旧版本继续按现有规则 `superseded`，只允许最新稳定版本发起专人操作转发。
- 同一线程已经成功转发后发生恢复或重复 worker 运行时，持久 delivery claim 必须阻止重复转发。
- 用户只是在询问流程、权限或系统行为时正常回答，不因出现“创建账号”“解冻”等词自动升级。
- 产品功能改动仍使用 `feature_request`；跨服务人工接管仍使用 `service_handoff`；已确认故障仍使用 `code_defect` 或 `technical_change`。
- 专人操作不授权客服模型执行任何写操作，也不改变生产只读边界。

## 验证

按测试驱动流程在本地创建临时回归用例，先确认当前代码会把信息齐全的专人操作错误判为 `ignore` 或无法通过 `human_operation`，再实现最小改动并确认用例通过。临时测试代码在提交前删除。

至少验证：

1. 结构化 schema 接受 `decision=escalate + human_operation + humanOperation`，拒绝缺少操作信息、标识为空以及非专人操作携带该结构的错误组合。
2. “创建运营账号”缺少名称时仍只追问一项，不转发。
3. 原问题加“kakaxi”补充后形成 `human_operation`，不再 `ignore`。
4. 信息齐全的用户解冻请求直接形成专人操作升级。
5. 单纯询问操作流程不会升级。
6. 服务端只在 action 和每个必要标识都能回查到完整原线程时接受专人操作，不要求代码或生产运行证据。
7. 技术群收到完整原问题和补充消息，且不会收到额外拼装告警文本。
8. 技术投递状态真实保存；重复 worker、发送不确定和运营回复失败继续遵守现有 ownership 规则。
9. 运营收到模型生成的确认与安抚回复，文案必须明确使用“已/已经通知”等完成态，不得把“需要通知/稍后通知”当作已经通知；同时阻断“账号已经创建、用户已经解冻、操作已经完成、技术已经处理”等未经证实的完成声明。
10. 相关现有测试、类型检查和前后端构建通过。

## 不在本次范围

- 不由机器人直接创建账号、解冻用户或执行其他生产写操作。
- 不增加技术群坐席分配、在线状态、确认接单或完成回执功能。
- 不新建人工工单表、第二个告警群或新的后台菜单。
- 不改变产品需求、跨服务接管和已确认故障的现有升级语义。
- 不部署、不启动或重启本机及生产客服服务。
