# 每日自动关闭全部 Telegram 群设计

## 目标

管理员可以在“运行配置”设置每日关闭时间。到达指定时间后，系统自动停用 SQLite 中全部 Telegram 群，包括客服群和技术告警群；Telegram 账号本身保持启用，管理员随后仍可在“群与账号”手动重新启用群。

项目固定维护路径更新为 `/Users/oldwang/Desktop/project/sfzf-telegram-ai-support`。实现完成后只部署到既有 Linux systemd 服务，本机不启动或重启常驻服务。

## 调研结论

成熟调度器把计划作为可更新的持久化资源，并保留下次或最近执行状态。BullMQ Job Schedulers 使用稳定 ID upsert 计划，Quartz 则显式定义停机或繁忙造成的 misfire 处理。本项目是单机、单进程、嵌入式 SQLite 架构，不应为一个每日任务引入 Redis，也不应把业务配置拆到 systemd timer。

参考：

- [BullMQ Job Schedulers](https://docs.bullmq.io/guide/job-schedulers)
- [Quartz CronTrigger Misfire Instructions](https://www.quartz-scheduler.org/documentation/quartz-2.5.x/tutorials/tutorial-lesson-06.html)

## 方案选择

采用 SQLite 持久化计划和应用内轻量 worker：

- 优于纯内存 cron：应用重启后计划不会丢失，并能处理错过的执行时间。
- 优于 systemd timer：配置、运行状态、迁移和后台展示都在同一个产品边界内。
- 优于外置队列：不增加 Redis、队列 worker 或新的生产依赖，符合现有部署规模。

## 数据模型

数据库 schema 升到下一个统一版本。新增单行计划表，保存：

- 是否启用每日自动关闭。
- 每日关闭时间，严格使用 `HH:mm` 24 小时格式。
- 固定 IANA 时区 `Asia/Shanghai`。
- 上次成功执行对应的上海本地日期。
- 上次成功执行时间和当次实际停用数量。
- 配置更新时间。

配置和运行态随主 SQLite 备份、导出和导入迁移。计划不保存账号凭据或其他秘密。

## 后端组件与数据流

新增职责单一的每日群关闭服务：

1. 读取当前计划。
2. 按 `Asia/Shanghai` 计算当前本地日期和分钟。
3. 当计划已启用、当前时间达到或超过计划时间，且本地日期尚未成功执行时，进入 SQLite 事务。
4. 在事务内再次读取并核对计划，原子执行 `UPDATE telegram_groups SET enabled=0`，随后记录本次日期、时间和实际关闭数量。
5. 同一天重复唤醒不再执行。

常驻 worker 每分钟唤醒一次，启动时立即检查一次。若应用在计划时间停机，当天晚些时候恢复，启动检查会立即补执行；如果跨过了当天且在次日计划时间之前启动，不追补前一天。配置时间改到当天当前时间之前时，只要当天尚未执行，就会在下一次检查补执行；当天已经执行过则不会因修改时间重复执行。

停用范围按 `telegram_groups` 全表处理，不按 `purpose`、账号、项目、服务或当前启用状态筛选目标类型，因此包括客服群、技术告警群以及未完整配置的草稿群。实际关闭数量只统计由启用变为停用的行。

worker 的启动和停止接入现有服务生命周期。执行失败只写脱敏内部日志并等待下一分钟重试，不向客服群或技术告警群发送消息。

## API 与后台

在现有运行配置 API 中返回并更新以下字段：

- `dailyGroupShutdownEnabled`
- `dailyGroupShutdownTime`
- `dailyGroupShutdownTimezone`
- `dailyGroupShutdownLastRunAt`
- `dailyGroupShutdownLastDisabledCount`

客户端只能更新开关和时间；时区及上次执行状态由服务端控制。时间必须严格匹配 `00:00` 到 `23:59`，未知字段继续由 Zod 拒绝。

“运行配置”的自动客服配置卡新增：

- “每日自动关闭所有群”开关。
- 时间输入框。
- 明确展示“中国标准时间（Asia/Shanghai）”。
- 上次执行时间和关闭数量；从未执行时显示“尚未执行”。

保存继续复用当前“保存运行配置”动作。关闭该计划只停止未来自动执行，不自动重新启用任何群。

## 并发、幂等与现有任务

SQLite 事务和上次执行本地日期共同保证单实例内同一天最多成功执行一次。即使手动群操作与计划同时发生，最终群状态仍为停用，计划执行记录与群更新在同一事务提交。

现有回答发送、进度发送和技术告警发送在发送前都会读取群启用状态；群被停用后，尚未发送的输出会被现有门禁阻断。本功能不删除问题线程、不取消模型任务、不停用 Telegram 账号，也不修改全局 `telegramEnabled`。

## 测试与验收

采用 TDD，至少覆盖：

- schema 迁移保留既有运行数据并创建默认关闭状态的计划。
- 配置 API 接受合法开关和时间，拒绝非法时间、运行态字段和未知字段。
- 到点前不关闭群。
- 到点关闭所有用途的群并记录准确数量。
- 同一天重复检查幂等。
- 应用在当天计划时间之后启动时补执行。
- 次日再次到点可以重新执行。
- 停用计划后不执行。
- 前端类型检查、全量 Vitest、服务端和前端生产构建通过。

生产部署使用既有受限本地部署配置解析目标和认证。部署前记录远端提交；拉取精确提交、安装锁定依赖、构建并重启既有 systemd 单元。部署后验证：schema 已升级、systemd active、`/health` 正常、服务只监听 `127.0.0.1:3210`，近期日志无迁移或 worker 错误。若失败则恢复部署前提交并重新构建重启，业务 SQLite 不替换、不清空。

## 非目标

- 不自动重新开启群。
- 不支持按群、项目、服务或用途选择关闭范围。
- 不支持每周、每月、cron 表达式或一次性日期时间。
- 不停用 Telegram 账号，不停止 Telegram 运行循环，不修改代码同步和自动学习开关。
- 不新增 Redis、外置调度服务或 systemd timer。
