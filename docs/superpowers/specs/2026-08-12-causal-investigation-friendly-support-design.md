# 深层因果排查与专业亲切客服语气设计

## 目标

AI 客服不能把请求或响应中的直接现象自动当作最终原因。遇到空字段、失败状态、上游拒绝、回调异常等情况时，需要在发送最终回复前结合当前已发布代码和可用只读资源继续追查字段来源、转换链路、运行配置和原始输入，尽可能直接确认唯一根源。只要当前绑定服务仍有可用证据路径，就不能把“还要再看”“需要再确认”当作最终答案发给运营。

运营回复继续保持简短中文，同时从偏直接的群聊口吻调整为专业、亲切、自然的客服口吻。回复应让运营感到 AI 正在耐心协助，但不使用固定称呼、模板式道歉或报告腔。

AI 确认根源后，如果处理方式需要技术人员修改代码、生产配置或后台映射数据，客服应先尝试把原问题、已确认根源和可信证据发送到技术告警群，再在原群说明具体根源并告知已经通知技术同事。即使技术告警群未配置、未启用或实际发送失败，运营文案仍按产品要求回复已经通知，后台继续保留真实发送结果。商户可以自行补充的参数和上游自身问题仍由客服直接说明，不通知技术。

## 已确认根因

当前回答规则已经要求 AI 先阅读代码并自主选择服务器、日志、数据库、Redis 或 nginx 等只读资源，但没有定义“原因已经查清”的完成标准。

同时，现有提示允许模型在消息本身证据足够时立即回答。模型因此可能把最靠近错误响应的事实视为完整原因。例如上游请求中的 `payBankCode` 为空只能证明最终发送值为空，不能区分原始订单没有银行编码和通道银行映射转换失败。

现有调查轨迹会验证模型记录的证据是否真实，却不会确定性判断任意业务问题的因果链是否已经完整。试图用固定表名、字段名或查询顺序解决这个问题会重新限制 AI 的自主排查能力，也无法覆盖不同服务和业务实现。

现有 `escalate` 流程能够向原群和技术告警群分别发送消息，但它只接受当前代码文件和行号已经验证的代码缺陷，并且会丢弃模型针对运营生成的具体原因，统一发送“这个问题还不能直接确认 我再跟进”。这与新要求相反：技术升级必须建立在根源已经确认的基础上，运营也应看到具体原因。现有流程还会先回复运营再尝试发送技术告警，需要调整为先尝试技术告警、再发送唯一一条运营回复。

## 行业方案调研

- OpenAI 的 Agent 构建指南建议把复杂流程拆成清晰动作，并为资料缺失和其他边界情况编写条件分支。适合本项目把“继续追查字段来源”和“证据不足时保留多个分支”写成明确完成标准，而不是增加 Maya 专项答案。
- Anthropic 的 Agent 设计建议让 Agent 在工具循环中持续取得环境真实证据，并只在完成或遇到阻塞条件时结束。复杂搜索可以增加 evaluator-optimizer，但应在简单方案不足时才增加复杂度。
- OpenAI Agents SDK 的客服示例使用明确客服角色、工具约束和逐步 routine。适合本项目在现有单 Agent 中同时明确专业亲切的客服身份和调查职责。

## 方案选择

### 采用方案

同步修改三层权威说明：

1. `AGENTS.md` 中长期维护的回答和运营语气规则。
2. `RuntimeKnowledgeService` 中写入 SQLite 的系统固定规则种子。
3. `CodexSupportDecisionAgent` 每轮回答直接使用的运行提示。

三层表达同一原则，避免项目记忆、后台固定规则和运行提示互相矛盾。系统固定规则种子改变后，服务下次启动执行 `ensureSystemDirectives` 时会用新种子整体替换 SQLite 中原有系统规则，同时保留对应证据事件。

回答结构增加明确的升级分类，区分普通回复、已确认代码缺陷和已确认需要技术执行的配置或后台数据处理。服务端继续验证升级证据，不能仅凭模型写出“需要技术”就发送告警。

### 不采用方案

- 不只修改提示词，否则后台展示的系统固定规则与实际行为不同。
- 不新增 Maya 单通道规则；银行编码的分支判断作为所有非印度服务的通用规则，同时用同一套因果完成标准覆盖其他派生字段和状态。
- 不恢复固定表名、固定日志或固定查询顺序，避免与不同服务实现冲突。
- 不增加第二个评估 Agent。当前问题有清楚的通用完成标准，额外模型循环会增加回答延迟和成本，也可能把无法确定性检查的业务因果关系误判为失败。
- 不移除升级证据校验。扩展技术处理范围不能退化成模型认为“客服解决不了”就随意通知技术。

## 深层因果排查规则

AI 应把本题证据分为两类：

- 直接现象：最终请求字段、响应错误、订单状态、日志中的失败结果或当前资源状态。
- 形成原因：产生该字段、状态或结果的原始输入、代码转换、映射、模板、配置、业务数据或外部事件。

当直接现象可能由上游数据经过代码或配置派生时，AI 必须沿当前代码反向追踪：

`最终结果 ← 字段转换或状态流转 ← 配置与业务数据 ← 原始输入`

排查要求：

1. 先确认当前代码中最终值的写入位置、取值来源和可能的转换分支。
2. 根据代码自主选择最有效的只读证据，核对转换前的值以及转换所依赖的配置或业务数据。
3. 不因看到明确错误文本就跳过其上游来源；错误文本只能证明它直接表达的事实。
4. 只要当前绑定服务还有代码、订单数据、日志、数据库、Redis 或运行配置等可用只读证据，必须继续执行下一项最有效的核对动作，不能提前生成面向运营的最终回复。
5. 只有证据排除了其他合理分支并指向唯一来源时，才把该来源写成确定原因，并直接给运营说明根源和对应处理方式。
6. 只有已经实际尝试当前所有合理且安全的证据路径，仍因外部信息确实缺失而无法区分时，才允许说明无法确认。此时只追问当前最少需要的一项外部信息，不把内部尚未执行的调查动作交给运营。
7. 规则不规定表名、文件名、日志框架或工具顺序，AI 继续根据当前服务代码自主选择调查路径。

以银行编码为空为例：

- 原始订单银行编码为空，可以判断商户下单或后台测试时没有填写银行。
- 原始订单银行编码有值但通道转换结果为空，应检查银行代码映射键和映射配置。
- 只有上游请求中的银行编码为空时，这只是调查起点。AI 必须继续读取代码确认字段来源，并查询原始订单参数和当前通道映射配置，不能停在“传给上游时为空”。

这只是规则示例，不作为 Maya 专项知识写入 AI 记忆库。

## 客服身份与语气

AI 的对外身份是熟悉业务、认真负责的专业客服。表达要求：

- 专业准确，先解决运营当前问题，不用随意猜测来换取确定语气。
- 亲切耐心，让对方感到 AI 愿意继续协助，而不是下指令或推卸责任。
- 使用自然口语，可以按上下文使用“我看了下”“我再确认下”“麻烦发下”等表达。
- 不固定使用“您好”“感谢理解”“非常抱歉”等模板开场，也不恢复“根据排查”“建议您”“请提供”等报告腔。
- 没有证据时不责怪商户、运营、上游或后台配置；有直接证据时客观说明事实和处理方向。
- 首次回复仍默认一到两行；亲切语气不能引入重复结论、无意义寒暄或冗长解释。
- AI 原始回复模式不受真人口吻的长度和语言限制，但仍遵守深层因果排查、安全和证据规则。

银行编码案例查到原始订单没有填写银行时可以回复：

```text
maya这笔下单时没有带银行 所以传给对方是空的
让商户把银行填上后再拉一次就行
```

查到原始订单有银行但 Maya 映射配置缺失时属于客服无法直接处理，完成技术告警发送尝试后回复：

```text
maya这笔下单有带银行 但maya的银行映射没配上 所以传给对方是空的
我已经通知技术同事处理了
```

不能只停在直接现象，也不能把未完成的调查发给运营：

```text
maya这笔传给对方的银行编码是空的
我再看下原订单有没有带银行和maya的银行映射配置
```

## 客服无法处理时的技术升级

技术升级必须同时满足：

1. 根源已经通过当前代码和实际只读运行证据确认，不是可能性、推测或资源查询失败。
2. 处理动作属于本服务内部，并且必须由技术人员执行写操作，例如修改代码、生产配置、通道映射配置或后台映射数据。
3. 商户、运营或上游无法通过其职责范围内的普通操作自行解决。

以下情况通知技术：

- 当前已发布代码中确认具体文件和行号的代码缺陷。
- 已确认生产配置缺失或错误，并且需要技术修改配置。
- 已确认通道映射或其他后台业务数据缺失、错误，并且需要技术写入或修正。

以下情况不通知技术：

- 商户下单参数没有填写，客服直接说明需要商户补充的内容。
- 上游拒绝、未回调或上游自身异常，客服直接说明当前根源和应联系的对象。
- 正常业务状态或正常状态流转。
- 仍未查清、证据冲突、只读资源失败或只是运营要求“交给技术”。这些情况必须继续排查，不能用升级代替确认根源。

结构化回答保留 `decision=escalate`，并增加升级类型以区分代码缺陷和已确认技术处理。`decision=escalate` 也必须携带一条不包含“已通知”的具体运营结论。服务端验证升级类型和可信调查步骤后，先尝试向技术告警群发送原问题、服务、来源群、已确认根源、运营结论和记录 ID。

升级过程中不先向运营发送“我去通知技术”“正在通知技术”或其他中间状态。完成技术告警发送尝试后，无论结果为 `sent`、`not_configured`、`failed` 或 `uncertain`，都按产品规则向原群一次性发送具体原因并追加“我已经通知技术同事处理了”。例如：

```text
maya这笔下单有带银行 但maya的银行映射没配上 所以传给对方是空的
我已经通知技术同事处理了
```

技术告警未配置、未启用、明确发送失败或发送结果不确定时，原群仍只发送同一条“具体根源 + 我已经通知技术同事处理了”。运营文案不随技术告警发送结果变化；后台回复记录和调查依据必须保存真实的 `sent`、`not_configured`、`failed` 或 `uncertain` 状态，不能篡改为已发送。整个升级过程不向运营发送通知前后的两条状态消息。

## 数据流与运行行为

每轮回答仍按现有流程读取当前服务代码快照、固定规则、相关记忆和只读资源。模型在形成最终回答前使用新的因果完成标准判断调查是否结束。正常情况下，运营收到的是已经确认的根源和处理方式，不是下一步调查计划。

调查轨迹继续只记录真实执行动作和证据，不要求展示隐藏推理。最终 `inference` 只能概括前述可信步骤。深层排查规则改变模型何时停止和如何表述证据不足，不改变调查轨迹结构、数据库查询审计或出站敏感信息阻断。

升级链路改为“可信证据校验 → 尝试发送技术告警 → 发送唯一一条固定升级语义的原群回复 → 保存两边真实发送状态”。技术告警发送前不向运营群发送升级状态，运营文案不依赖技术告警投递结果。代码缺陷继续验证当前快照中的仓库、文件和行号；配置或后台映射数据问题必须至少有与根源直接相关的实际只读运行证据，不能只使用模型推断步骤或代码快照元数据。

## 错误与边界处理

- 资源不可用但消息已有明确证据时，保留该直接事实，不把它降级成完全无法判断。
- 实际尝试当前所有合理证据路径后，资源仍不可用且无法确认唯一根因时，说明已确认事实并只追问当前缺少的最小外部信息，不暴露内部执行错误，也不使用“我再查一下”掩盖调查未完成。
- 多项证据冲突时保留冲突，不选择方便回答的一方。
- 达到回答时间上限时按现有兜底规则回复，不能为了求根问底无限等待。
- 因果链未确认不构成升级条件。只有已确认代码缺陷，或已确认需要技术修改的生产配置和后台映射数据问题，才升级技术群。
- 技术告警发送成功但原群回复失败时，保留技术告警真实成功状态，并按现有运营群发送失败流程补充技术告警，不能重复发送运营回复。

## 验证

按用户要求不新增测试文件或测试代码。实施后执行现有相关测试、类型检查和构建，并重点检查：

1. 三层规则内容没有互相矛盾。
2. 系统固定规则种子变化能够被 `ensureSystemDirectives` 识别并在下次启动时替换。
3. 真人口吻同时包含专业亲切要求和现有简短、少标点、非报告腔约束。
4. AI 原始回复模式没有被真人口吻限制误伤。
5. 深层排查规则没有引入固定表名或固定查询顺序，新增技术处理升级仍要求已确认根源和可信运行证据。
6. 商户漏传参数不升级，已确认需要技术修改的映射配置问题能够升级。
7. 技术告警无论成功、未配置、失败或结果不确定，运营都只收到一次“已经通知技术同事处理了”；后台状态仍忠于真实投递结果。
8. 技术告警包含原问题、具体根源和必要可信证据，并继续经过脱敏。
9. 升级过程中运营群只收到一条最终回复，不出现“我去通知”与“已通知”两条连续消息。
10. 现有构建和测试通过。

## 不在本次范围

- 不新增 AI 记忆或人工纠正记录。
- 不新增地区分组或修改记忆检索结构。
- 不增加第二个模型或评估循环；结构化输出只增加本次升级证据校验需要的升级类型。
- 不修改服务器、生产数据库、Redis 或部署流程。
