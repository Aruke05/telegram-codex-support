# 白名单群快捷启停与批量配置设计

## 目标

在“群与账号 > 白名单群”列表中提供客服群单行即时开关，并为多选群提供原子化的批量启用、停用和配置能力。批量配置只修改接入方式、客服账号和回复方式；项目归属、群用途、技术告警群模型及群基础信息保持不变。

## 调研结论

- Open WebUI 的管理端把启用状态作为可筛选、可批量启停的持久配置，说明批量状态操作应当直接作用于后端权威状态，而不是只维护临时前端状态。
- Chatwoot 的状态切换由明确的服务端动作保存，前端只负责发起操作和呈现结果，适合本项目现有 SQLite 权威配置模型。
- WAI-ARIA Switch Pattern 建议二元启停使用带稳定标签的原生开关语义；本项目沿用原生 `input[type=checkbox]`，保留键盘操作、焦点状态和可读标签。

本项目不照搬大型系统的通用批处理框架。当前只有约 14 个群，采用一个严格校验的 SQLite 事务即可满足一致性和性能要求。

## 列表交互

- 每个白名单群显示多选框，支持逐项选择和当前列表全选。
- 有选择时显示批量操作栏，包含“批量启用”“批量停用”“批量配置”“取消选择”和已选数量。
- 客服群行内显示即时启停开关；技术告警群不显示行内开关，降低误关告警的风险。
- 单群和批量请求进行时锁定相关控件，防止重复提交。
- 成功后以服务端返回结果刷新列表；失败时恢复原状态、保留选择，并显示服务端给出的中文原因。
- 窄屏下批量栏允许换行，行内选择框、状态、开关和操作按钮不得横向溢出。

## 批量配置

批量配置弹窗允许按需修改以下字段：

- 接入方式：Bot 或个人账号。
- 客服账号：根据最终接入方式筛选账号。
- 回复方式：真人口吻或 AI 原始回复。
- 触发方式：只读展示固定规则，客服群为“每条文字都判断”，技术告警群为“仅 /ai”。

每个可修改字段提供“不修改”。接入方式和客服账号遵循以下联动：

- 选择新的接入方式后，必须选择该类型的客服账号。
- 未统一接入方式时，只有全部所选群当前接入方式相同，才允许只修改客服账号。
- 所选群接入方式混合时，客服账号控件提示先选择统一接入方式。
- 回复方式可以独立修改。
- 未选择任何变更时不提交请求，并在弹窗内提示。

批量配置不修改 `projectId`、`serviceId`、`purpose`、`aiModelInstanceId`、群 ID、名称或标识。触发方式不由客户端写入，服务端继续按现有固定规则校验。

## 后端接口与事务

新增批量更新接口，接收唯一群 ID 列表和严格白名单补丁：

```ts
type BatchGroupPatch = {
  enabled?: boolean
  accessMode?: "bot" | "user"
  accountId?: string
  replyStyle?: "human" | "unrestricted"
}

type BatchGroupUpdateInput = {
  ids: string[]
  patch: BatchGroupPatch
}
```

请求至少包含一个群 ID 和一个允许修改的字段；拒绝重复 ID、未知字段、缺失群和空补丁。服务层先读取全部群，构造候选配置并执行现有账号、项目、服务、群用途和技术群模型校验。全部候选有效后，才在一个 SQLite 事务中更新；任一候选失败则整批保持不变。

单群即时开关复用同一批量服务方法，只传一个群 ID 和 `enabled`，避免单群与批量规则漂移。现有普通群编辑接口继续用于完整配置。

批量启用时必须满足：

- 已绑定且已启用的客服账号与接入方式一致。
- 客服群原有项目和服务绑定有效。
- 技术告警群原有专属模型存在且已启用。

服务端返回更新后的群视图；错误信息列出首个失败群及具体原因，不包含凭据或连接信息。

## 运行语义

- 停用提交成功后，Telegram 接入和问题线程协调器立即拒绝该群的新消息。
- 已落库但尚未开始生成的问题不再发送回复。
- 已经进入生成阶段的回复不强制中断，完成后不再处理新消息，避免发送结果归属不明。
- 重新启用只接收之后到达的新消息，不恢复已关闭的问题线程。
- 群启停不影响后台项目代码同步资格，继续只由项目与服务配置决定。

## 测试与验证

后端采用 TDD 覆盖：

- 单群启用和停用。
- 多群批量启用和停用。
- 批量修改接入方式、客服账号和回复方式。
- 混合群用途时固定触发规则保持不变。
- 任一群无效时全部回滚。
- 重复 ID、缺失群、空补丁和未知字段被拒绝。
- 项目归属、群用途、技术群模型和其他未选择字段保持不变。

前端把选择状态和批量表单约束提取为纯函数测试，覆盖全选、取消、混合接入方式、账号过滤、空变更和请求载荷。完成后运行完整测试、类型检查和生产构建，并在桌面与窄屏、浅色与深色模式下真实检查列表、批量栏和弹窗。

## 部署与回滚

- 只提交本功能文件，不纳入工作区已有的文档删除和未跟踪内容。
- 使用中文提交信息推送 `telegram-ai-support` 分支。
- 在既有指定 Linux 服务器拉取精确提交，保留现有 SQLite，不执行结构迁移。
- 安装依赖并构建后由 systemd 重启服务。
- 验证服务只监听 `127.0.0.1:3210`，检查 `/health`、systemd 状态和脱敏后的近期日志。
- 若部署验证失败，恢复上一提交，重新构建并启动；业务 SQLite 始终保留。
