# 群级影子学习模式设计

## 目标

在正式开启机器人群回复前，为选定客服群提供可批量启用的影子学习模式。系统按正式链路接收消息、拆分问题、只读排查并生成答案，但不执行任何普通客服相关 Telegram 输出。可信真人回复到达后，系统按拆分后的问题单元建立对应关系，在指定时间生成对比学习报告。报告只供人工查看，不自动更新固定规则、AI 记忆或真人口吻。

首份报告固定在 `2026-08-20 23:00 Asia/Shanghai` 生成。报告生成后群仍保持影子学习模式，由管理员查看报告后手动批量切换为正式回复。

## 非目标

- 不在影子学习期间自动发布知识或修改回复风格。
- 不把整个群或固定时间窗口当成一个无法拆分的对比单元。
- 不在影子模式下发送客服回复、进度提示、技术告警或异常兜底消息。
- 不改变 `/start`、`/info` 等全局身份命令。
- 不通过学习报告执行生产写操作、代码修改、部署或外部通知。

## 群配置与批量操作

客服群增加运行模式 `live` 与 `learning`：

- `live`：沿用当前正式回复行为。
- `learning`：完整生成影子答案，但禁止普通客服相关 Telegram 输出。

技术告警群不允许配置学习模式。单群编辑页面展示运行模式；白名单群列表显示“正式回复”或“学习模式”徽标。现有批量配置支持对选中的客服群原子切换运行模式；混入技术告警群时返回明确中文错误且整批回滚。

运行模式必须在线程创建时固定到 `support_threads`。后台切换群模式只影响之后创建的问题，不得让已经开始的影子任务突然获得发送权限，也不得让已经开始的正式任务中途静默。

## 影子回答数据流

学习模式复用正式回答链路：

1. Telegram 原消息按现有规则原样入库。
2. 群级滚动语境和路由模型把输入拆分成一个或多个问题单元。
3. 每个问题线程按固定的模型、回复风格、代码快照和资源权限执行正式只读排查。
4. 回答模型生成结构化决策、答案、引用和拟执行升级动作。
5. 发送前统一影子输出门禁阻止 Telegram RPC。
6. 影子答案及“正式运行时本应执行的动作”持久化，线程以影子完成状态收口。

`support_replies` 继续承担一次回答生成的公共生命周期，并新增明确的影子终态；独立的影子结果表保存决策、答案、拟发送目标、拟告警类型和门禁审计。影子结果不能伪装为 `replied`、`escalated` 或任何已发送状态，不能生成 Telegram output ownership。

所有普通客服发送路径必须同时经过统一门禁，包括最终回复、最少追问、进度提示、产品需求通知、故障升级、专人操作升级、跨服务接管和失败收口。门禁以线程固定模式为准，不读取可能已变化的群当前模式。身份命令不关联客服线程，因此不受该门禁影响。

## 真人答案与拆分问题匹配

真人标准答案只来自后台“用户与角色”中同时满足以下条件的数字 Telegram ID：

- 角色已启用；
- `learning_source_enabled=1`；
- 消息来自启用的客服群；
- 消息原文和附件已正常审计入库。

学习模式下，可信真人回复不得取消或中止仍在生成的影子答案。系统建立真人消息与拆分问题线程之间的多对多关联：

1. 直接回复某个问题原消息、机器人历史回复或同一回复链时优先确定关联。
2. 一条原消息被拆成多个问题、真人回复又覆盖多个问题时，由匹配模型结合原始拆分结果、真人回复和只读群级语境返回零个、一个或多个问题 ID。
3. 每个匹配必须带置信度和理由；低置信度、找不到对应问题或存在无法消除的歧义时只保留审计，不进入报告对比。
4. 一条真人回复可以关联多个问题；一个问题也可以累计多条可信真人回复。报告生成时按消息时间组合该问题的真人答案，不把其他问题的回复混入。

正式模式继续沿用当前真人接管并取消机器人任务的行为。只有固定为学习模式的线程使用“不取消影子生成”的关联路径。

## 对比分析

对比单元是 `问题线程 + 输入版本 + 影子回答`，而不是整个群。报告任务为每个拥有可信真人答案的影子回答生成结构化比较，至少包括：

- 问题理解和拆分是否正确；
- 影子答案与真人答案的共同结论；
- 事实错误、证据不足或责任判断偏差；
- 遗漏的业务信息、处理动作或必要追问；
- 影子答案中真人没有采用的多余内容；
- 可靠性、真实性和可执行性评分；
- 语言长度、分段、措辞、合作姿态和拟人性差异；
- 建议保留、修改或人工复核的具体事项。

没有可信真人回复的问题计入“未获得真人对照”统计，但不得让模型猜测标准答案。影子任务失败、代码快照不可用或输出被安全门禁拒绝时保留真实失败原因，并计入覆盖率和失败率。

对比模型只能读取当前报告范围内的影子结果、已匹配真人消息、当时固定的代码与记忆引用和安全审计字段，不得触发服务器写操作、Telegram 发送或生产资源访问。报告内容再次经过出站敏感信息阻断，不展示 Token、密钥、Session、数据库密码、私钥、商户密钥和连接凭据。

## 报告生成与展示

新增持久化的一次性报告计划，首个计划时间为 `2026-08-20T15:00:00.000Z`，即上海时间 `2026-08-20 23:00`。计划具备以下语义：

- 到期后只由一个 Worker claim，服务重启可恢复且不会重复生成。
- 若服务在计划时间未运行，恢复后立即补生成。
- 报告截止时间固定为计划时间，晚到消息不悄悄改变已完成报告。
- 生成报告不切换任何群的运行模式。
- 后台提供“立即生成报告”，创建新的报告任务但不覆盖历史报告。

“AI 记忆库”增加“学习报告”入口。报告列表显示时间范围、覆盖群数、问题数、有真人对照数、成功影子答案数和失败数。报告详情按群和拆分问题展示原问题、影子答案、真人答案、结构化差异、评分、证据引用和匹配置信度，并提供只读筛选与展开查看。

报告不提供“一键自动应用全部建议”。后续若需要采纳，管理员应通过现有人工新增记忆、人工纠正或独立审核流程明确提交。

## 数据结构

数据库统一升级到新的 schema version，并新增或扩展以下能力：

- `telegram_groups.operation_mode`：`live | learning`，默认 `live`。
- `support_threads.answer_operation_mode`：创建线程时固定的模式。
- `support_replies`：新增不代表投递成功的影子终态。
- `shadow_answer_results`：保存影子决策、答案、拟执行动作、门禁原因和生成审计。
- `shadow_human_answer_links`：真人消息与拆分线程/输入版本的多对多关联、匹配方法、置信度和理由。
- `shadow_comparisons`：逐问题结构化对比结果及模型运行终态。
- `shadow_learning_reports`：报告计划、claim、范围、汇总、正文和完成状态。
- `shadow_learning_report_items`：报告与逐问题对比的稳定关联。

原始 Telegram 消息和影子回答遵守客服记录 90 天保留期；由人工明确采纳后形成的记忆仍按现有记忆保留规则处理。报告不得通过复制完整敏感聊天规避保留期，历史详情在原记录清理后只保留脱敏汇总、稳定统计和不可逆引用标识。

## 并发、恢复与幂等

- 同一问题输入版本只允许一个有效影子结果；补充消息增加输入版本后旧影子结果标记为 `superseded`。
- 真人消息重复投递不得重复创建链接。
- 匹配任务和报告任务使用持久 claim、锁令牌、心跳和有限重试。
- 模型失败只记录失败，不生成固定对比结论。
- 影子完成与真人消息到达顺序无关；任一先到都能在另一方到达后形成可报告单元。
- 报告生成按固定截止时间读取稳定快照，完成后不可静默重写，只能创建新报告版本。

## 安全门禁

影子模式的核心不变量是：普通客服问题的 Telegram RPC 数量必须为零。测试必须覆盖每一种决策和异常分支，并验证：

- 没有客服回复、进度消息或技术告警发送；
- 没有 Telegram output ownership；
- 影子结果完整落库；
- 群模式中途切换不改变线程固定权限；
- `/start`、`/info` 仍正常工作；
- 正式模式行为不回归。

## 测试策略

1. 数据库迁移、导入导出和旧库默认正式模式测试。
2. 单群和批量 API 原子更新测试。
3. 前端批量表单、徽标和技术群禁用测试。
4. 回答 Worker 对 reply、ignore、clarification、escalation、progress 和异常收口的零输出测试。
5. 一条消息拆多问题、一条真人回复匹配多问题、多条真人回复匹配单问题和歧义拒绝测试。
6. 报告计划的指定时间、错过补跑、并发 claim、失败恢复、截止时间稳定和不自动切换模式测试。
7. 报告脱敏、无自动记忆写入和客服记录保留期测试。
8. 完整类型检查、全量测试和构建验证。

## 上线顺序

1. 部署数据库迁移和默认 `live` 模式，确认现有群行为不变。
2. 批量将选定客服群切换为 `learning`。
3. 验证影子任务产生、Telegram 普通客服输出为零、可信真人答案能够匹配拆分问题。
4. `2026-08-20 23:00 Asia/Shanghai` 自动生成首份报告。
5. 管理员查看报告后，手动批量把确认上线的群切换为 `live`。
